# Backend Parity — 실행-증거 패리티 런 엔진 (v2.11.0)

## Role
모니터링 카탈로그의 모델 × API surface × 피처 매트릭스를 실제 API 호출로 검증한다.
**HTTP 200은 증거가 아니다** — 응답 내용이 증거 검사를 통과해야 `supported`.
결과는 `parity_runs` / `parity_results` 테이블에 저장되고 `/parity` 페이지가 렌더링한다.

## Files
- `catalog.py` — `SURFACES` 6개 (converse / invoke_model / messages / messages_mantle / chat_completions / responses), `FEATURES` 20개 (각 항목 label_ko/desc_ko + label_en/desc_en — 프론트 현지화용, v2.16.2) (기본 7 + v2.14.0: adaptive_thinking, count_tokens, batches, web_search, computer_use + v2.15.0: reasoning_effort, json_schema, url_sources, memory_tool, code_execution, files_api, models_api + v2.34.0: strict_tool_use — `_FEATURE_SURFACES` 맵으로 surface 제한, json_schema와 strict_tool_use는 제한 없이 6 surface 전부). Admin/Usage API·MCP connector는 정직한 판정 불가로 의도적 제외. `surfaces_for(model_id)` — model_id 접두사로 surface 결정 (Bedrock Claude CRIS는 messages_mantle 포함, in-region `bedrock:<region>:` 키는 converse + invoke_model만 — Mantle은 us-east-1에 같은 FM id를 보내 Global 행과 중복이고 서울 측정도 아니다, v2.32.0), `mantle_fm_id()` — 프로파일 접두사 제거, `is_applicable()` — reasoning은 `_REASONING_MARKERS` 모델만
- **messages_mantle** (v2.13.0): Bedrock Mantle `/anthropic` 엔드포인트 시험 — `aws-bedrock-token-generator`의 SigV4 파생 bearer + FM id, 리전 `MANTLE_ANTHROPIC_REGION` — env 미주입 시 코드 폴백은 `ap-northeast-1`이지만, CDK가 backend와 모든 스케줄 태스크에 `us-east-1`을 명시 주입한다(2026-09-05 결정 — `ap-northeast-1`은 `/anthropic`에서 Opus 4.8만 서빙). 따라서 배포 환경의 `messages_mantle`과 Claude API Features Mantle 열은 둘 다 `us-east-1`을 프로빙한다. 리전이 서빙하지 않는 FM id는 `does not exist` 오류로 오고, `engine.classify_error`가 unsupported(명시적 미지원)로 판정한다. 보내는 id는 `catalog.mantle_fm_id`가 프로파일 접두사와 Bedrock 버전 접미사(`-20251001-v1:0`, `-v1`)를 뗀 값이다 — Mantle `GET /v1/models`(Authorization Bearer 하나만, x-api-key와 같이 보내면 401)는 `anthropic.claude-haiku-4-5`로 서빙하고 접미사 붙은 id는 404라 v2.34.0 전까지 Haiku 4.5 Global, US 두 행의 Mantle 셀이 전부 unsupported였다(2026-10-21). us-east-1 Mantle의 Claude는 fable-5, haiku-4-5, opus-4-7, opus-4-8, opus-5, opus-5-5, sonnet-5이고 Fable 5.1, Sonnet 5.5, Haiku 5.5, Sonnet 4.6, Opus 4.6은 없다(같은 날)
- `engine.py` — 순수 판정 로직 (외부 의존 없음, 단위 테스트 대상): `classify_error()` (`_UNSUPPORTED_MARKERS` 시그니처 → unsupported, 그 외 → broken — bedrock-runtime의 coral 라우트 부재 `UnknownOperationException`도 unsupported: Global/US CRIS OpenAI 호환 엔드포인트에는 `GET /v1/models/{model}`이 없고, XML 본문이라 openai SDK 문자열에 "Error code: 404"가 없어 run #211까지 `models_api` 11셀이 broken이었다. Mantle `/anthropic` Fable 5의 데이터 보존 거부 "is not available for this model"도 unsupported — `claude_features.engine`과 같은 판정, 사용자 결정 2026-10-19, run #211까지 32셀 broken), `check_canary` / `check_json_object` / `check_tool_roundtrip` / `check_cached_tokens` / `check_stream_events` / `check_schema_keys`(json_schema — 응답 키 집합이 스키마와 정확히 같은지) / `check_strict_tool_input`(strict_tool_use — 입력 키가 스키마 properties와 같고 값 타입이 맞고 카나리 왕복, v2.34.0)
- `probes.py` — surface별 실행기 5개. `CANARY`, `max_tokens_for(feature)` (structured_output 512 / 기본 256 / reasoning 2048), adaptive_thinking 프로브는 `max_tokens_for`를 거치지 않고 `_ADAPTIVE_MAX_TOKENS` 8000을 직접 쓴다(2048이면 adaptive가 thinking을 생략 — run #8), `_CACHE_PAD` (최소 캐시 토큰 초과용 장문 패딩). 클라이언트는 `prober.py` 헬퍼 재사용
- `runner.py` — `run_parity()`: ParityRun row 생성 → job 팬아웃 (skipped는 프로브 없이 기록) → ThreadPoolExecutor(4) → 결과 메인 스레드 일괄 저장 (스레드별 DB 세션 금지). `_execute`가 converse, invoke_model에서 `prober._bedrock_target`으로 client 리전과 FM id를 함께 푼다(in-region 키, v2.32.0). `ParityResult.model_id`에는 키를 그대로 기록한다
- **OpenAI 클라이언트는 prober와 따로 둔다** (v2.28.2): `runner._parity_openai_client`가 SDK 기본값(timeout 600s, `max_retries` 2) 클라이언트를 만든다. prober `_get_openai_client`의 `max_retries=0` + read 60s는 대시보드 프로브 hang 대책이고, 패리티에 적용하면 SDK가 재시도해 주던 429/5xx/연결 오류가 `classify_error`에서 broken 셀이 된다. 공유하는 것은 자격증명 선택(`prober._openai_api_key`)뿐 (테스트: `tests/test_parity_openai_client.py`)

## Entry Points
- 스케줄: EventBridge 12시간 주기(rate 12 hours) → Fargate `python -m parity_runner --once` (모델 discovery 후 `run_parity()`)
- 수동: `POST /api/parity/trigger` (JWT) — backend 프로세스 내 백그라운드 스레드 (Fargate 아님)

## Gotchas
- **판정이 이상하면 프로브 결함부터 의심**: `max_tokens`가 모자라 출력이 잘리면 모델 문제가 아닌데도 증거 검사가 실패해 Broken이 된다(`probes.max_tokens_for`가 피처별 예산을 두는 이유). Broken 셀은 `/api/parity/evidence`의 `response_snippet`으로 원인 확인. 예산만으로 부족하면 프롬프트로 출력 길이를 묶는다 — `_JSON_PROMPT`의 "키는 5개 이하"가 없을 때 Opus 5 JSON이 209~591토큰이라 512 예산에서 간헐적으로 잘렸다(run #190, #200, #208, #211, 2026-10-19 수정)
- 피처 추가 시: `catalog.py` FEATURES + `probes.py` 5개 실행기 모두 + `is_applicable()` 규칙. 모델 목록은 자동 반영 (`prober.AVAILABLE_MODELS` 순회)이지만, 새 모델마다 `catalog.py`의 `_REASONING_MARKERS`(reasoning 적용 대상, substring 매칭)와 `_NO_FORCED_TOOL_CHOICE_MARKERS`(forced `tool_choice` 400 → tool_use를 auto + 지시로 대체)를 검토한다 — 둘 다 substring이라 짧은 마커가 형제 모델까지 잡는다(예: `"opus-5"`를 넣으면 Opus 5도 auto). 현재 `_NO_FORCED_TOOL_CHOICE_MARKERS`는 `fable-5-1`, `opus-5-5`, `sonnet-5-5`(v2.32.0)이고 `"sonnet-5"`는 넣지 않는다 — 서울 in-region Opus 5, Sonnet 5는 forced `tool_choice`를 200으로 수락한다(2026-09-30). v2.33.0의 Sonnet 5.5 US 채널도 forced 400이라 기존 `sonnet-5-5` 마커가 덮는다. Claude Haiku 5.5(v2.33.0)는 forced `tool_choice`를 Bedrock과 CP 모두 200으로 받아 이 마커에 넣지 않고, `thinking.type.enabled` 400과 adaptive + effort 200(Sonnet 5.5처럼 adaptive 전용)이라 `_REASONING_MARKERS`에 `"haiku-5"`를 더했다(haiku-4-5는 해당하지 않는다, 2026-10-07). GPT 6.1 Sol도 `reasoning_tokens` 0이라 `_REASONING_MARKERS`에 `gpt-6`을 넣지 않는다
- **구조화 출력 프로브 (v2.34.0, AWS 문서 2026-10-19)**: `json_schema`는 Claude 본문 `output_config.format`(스키마는 객체), Converse `outputConfig.textFormat`(`structure.jsonSchema.schema`는 JSON 문자열)을 쓰고 beta 헤더는 없다(구 `output_format` + `structured-outputs-2025-11-13`은 CRIS에서 아직 통하지만 문서 형식이 아니다). 증거는 "키가 있는가"가 아니라 "키 집합이 스키마와 같은가"다 — `_SCHEMA_PROMPT`가 스키마와 다른 키 이름(name)을 요구해, 스키마가 조용히 무시되면 name이 나와 broken이 된다(실측: 스키마 있음 45/45 city, 없음 9/9 name). 스키마에 없는 **정보**(국가, 인구)를 요구하지 말 것 — GPT가 그 정보를 city 값에 몰아넣다 GPT 6 Astra, GPT 6 Sol이 512토큰까지 반복 생성해 잘렸다. `strict_tool_use`는 integer 인자(`count`)에 문자열 "three"를 요구해 strict 무시를 타입으로 잡는다(strict 없이 Haiku 5.5, Sonnet 4.6, GPT 5.6 Luna가 문자열, strict면 전부 정수). 단 forced `tool_choice`를 못 쓰는 auto 모델(`_NO_FORCED_TOOL_CHOICE_MARKERS`)은 타입 충돌 지시에 thinking으로 고민하다 256토큰에서 잘리거나 Fable 5.1은 호출을 거절해서, `_strict_tool_prompt`가 정상 지시(`count` 3)로 바꾼다 — 이 모델들은 키와 타입만 검사한다. 2026-10-20 전수 2회: json_schema, strict_tool_use 모두 broken 0
- **서울 in-region 온디맨드 FM은 구조화 출력을 거부한다** (2026-10-20): `output_config.format`, 도구 `strict` 모두 400 "Extra inputs are not permitted"(Converse도 같다) → unsupported. 같은 요청의 응답 `model`은 Global과 같은 `claude-opus-5`이고 `output_config.effort`, adaptive thinking, 캐시 TTL 1h, beta 헤더는 받으므로 모델 버전이 아니라 그 서빙 경로의 미지원이다. Opus 5 모델 카드는 bedrock-runtime Structured outputs 지원과 서울 In-Region 제공을 함께 적고 있어 문서와 다르다. 서울 Mantle(`bedrock-mantle.ap-northeast-2`, Opus 5와 Sonnet 5 서빙)도 같은 두 필드를 같은 문구로 거부하고 effort는 받는다 — us-east-1, us-west-2, ap-northeast-1, eu-west-1 Mantle은 json_schema, strict 모두 supported(2026-10-21)라 서울 리전 서빙 쪽 차이다(패리티 Mantle surface는 us-east-1만 프로빙). Nova 2.0 Lite도 "doesn't support the outputConfig field", "doesn't support the strict field"로 unsupported, GPT 추론 모델의 Chat Completions strict 도구는 `tool_use`와 같은 "Function tools with reasoning_effort are not supported" 제약(supported 5, unsupported 23)
- 알려진 지속 이슈 (모델측, run #211 2026-10-19 기준): Fable 5 캐싱이 Converse/CP-Messages에서 cacheRead 0이고 InvokeModel도 run #204부터 두 번째 호출이 캐시를 다시 쓴다(cache_creation 9462, read 0), Fable 5 adaptive_thinking은 text 블록만, GPT 5.4, 5.5, 5.6 일부 채널은 `reasoning_tokens` 0, GPT 캐싱과 GPT 5.6 Sol (us-east-1) web_search 401 "not authorized for this identity"는 런마다 바뀐다
- 테스트: `backend/tests/test_parity_logic.py` (catalog + engine 순수 로직) + `test_parity_openai_client.py` + `test_parity_structured_outputs.py` (v2.34.0 — json_schema GA 형식과 beta 헤더 없음, Converse `outputConfig.textFormat`, strict 도구 요청 형식, 무시된 스키마와 문자열 count가 broken인지, 가짜 클라이언트) — `cd backend && python3.12 -m pytest tests/test_parity_logic.py tests/test_parity_openai_client.py tests/test_parity_structured_outputs.py -q`.
